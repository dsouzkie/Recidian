## 0. Project Identity

**Name:** RECIDIAN
**Why:** From "recidivism" — the tendency to repeat an offense. RECIDIAN scores the *recidivism risk* of a return/refund: is this order likely to become part of a repeat-abuse pattern (wardrobing, serial no-fault returns, promo-exploit returns), not just "is this one return suspicious."
**Tagline (for pitch):** *"Not every return is a loss. RECIDIAN tells you which ones are."*
**One-line pitch:** A defense-only, explainable risk scorer that intercepts Razorpay refunds in real time, flags high-risk returns before they're approved, and reports honestly-measured precision, recall, and false-positive cost — integrated with Razorpay's test-mode APIs and hosted at zero cost.

## 1. Fixed Constraints (do not deviate)

These are hard rails. Any implementation decision that conflicts with these should be rejected, not worked around.

1. **Loss class: RETURNS/REFUNDS ONLY.** Do not build fraud or chargeback logic. If a feature or idea drifts toward "detect fraudulent transactions," cut it. Scope creep across loss classes is the #1 way this project fails to finish.
2. **Defense-only.** The system may only score, flag, explain, and route for human review. It must never generate, simulate, or automate an abuse pattern (no "fake abusive customer generator" shipped as a feature, even for testing — keep any adversarial/red-team data generation as a private offline script, never a live capability of the shipped app).
3. **Zero cost, end to end.** No paid API tier, no paid hosting tier, no paid database, no credit card requirement anywhere in the stack. See Section 6 for the exact free-tier stack.
4. **Held-out test set is mandatory.** No metric is reported unless it comes from data the model did not train on. A single train/test split (80/20, stratified by label) is the minimum bar; a 3-fold cross-validation is the target if time allows.
5. **Every reported number must include false-positive cost.** Precision and recall alone are not enough — the deliverable is not complete without a cost-of-false-positive statement (Section 4.4).
6. **Time budget: 9 hours of active build time, hard cap.** If a task is running over its allocated slot in Section 5, cut scope, don't extend time. Cutting scope means removing a feature from the model or simplifying the UI — never means skipping the metrics/audit-trail work.
7. **Synthetic data only, generated by you, not scraped or copied.** No real customer data, no scraped e-commerce datasets with unclear licensing. Data must use Razorpay's exact field naming conventions (Section 3.5).
8. **Audit trail is a first-class deliverable, not a nice-to-have.** Every score the system produces must be logged with: input features, output score, decision threshold used, and a human-readable reason (from SHAP values or from the rule layer). This is what makes the system "explainable," which judges will ask about.
9. **Razorpay API integration is a first-class demo feature.** The live demo must show a real Razorpay test-mode transaction flow (Create Order → Capture Payment → Request Refund → RECIDIAN scores it), not just pasting JSON into a form.

## 3. Data & Feature Design

### 3.1 Critical: Returns = Refunds in Razorpay's World

> **Razorpay has no "returns" API.** In Razorpay's payment ecosystem, a return is modeled as a **refund** on a captured payment. The Refund API (`/v1/payments/:id/refunds`) creates `rfnd_` prefixed objects. There is no native `return_reason_code` field — return reasons must be stored in the `notes` object on the refund.
>
> This means: every reference to "return" in this codebase is operationally a "refund" at the Razorpay API level. The synthetic data and all API endpoints must reflect this.

### 3.2 Unit of analysis
One row = one **order-with-refund** (not one return event) — because you want to score risk *before* a refund is approved, or at the moment it's requested. Orders without refund requests are included as negative examples.

### 3.3 Label definition
`is_abusive_return` (binary) — synthetically assigned based on an underlying "customer archetype" you define, not assigned randomly. This is the single most important design decision for making your metrics mean something.

Define at least 4 customer archetypes when generating data:
| Archetype | Return/Refund behavior | Label |
|---|---|---|
| Normal shopper | Occasional refund, standard reasons (wrong size, damaged) | Not abusive |
| Loyal high-frequency shopper | Refunds often *because* they order often — refund rate looks high but is proportionally normal | Not abusive (this is your hard negative — critical for realistic overlap) |
| Wardrober | Buys, uses once (e.g. event wear), requests refund within narrow time window, high-value items, low re-purchase | Abusive |
| Serial/promo abuser | Refunds immediately after promo code applied, or refunds paired with a new order at full price shortly after, or refunds disproportionately vs. peer group | Abusive |

**Why the "loyal high-frequency shopper" archetype matters:** without it, your abusive class will be trivially separable on "refund count" alone, and a judge who asks "did you just threshold on refund count?" will be right. Including this archetype forces the model to use multiple features together, which is what makes your precision/recall numbers credible.

### 3.4 Candidate features (10–14 is plenty — do not over-engineer)
- `return_rate_90d` — refunds / orders in trailing 90 days
- `order_to_return_days` — days between order `created_at` and refund `created_at`
- `item_value_percentile` — value of refunded item vs. customer's typical order value
- `promo_code_used` (bool) — from `order.notes.promo_code`
- `days_since_promo_and_order` — proximity of order to a promo campaign
- `account_age_days` — customer tenure
- `orders_last_90d` — total order volume (to normalize return_rate against, avoiding the false-positive trap above)
- `category_return_rate_deviation` — this customer's refund rate for the category vs. category baseline
- `same_day_reorder_after_return` (bool) — reordered a similar item shortly after requesting refund
- `return_reason` (categorical: `damaged` / `wrong_size` / `not_as_described` / `no_reason` / `changed_mind`) — from `refund.notes.return_reason`
- `address_mismatch_flag` (bool) — shipping vs. billing mismatch, mild signal
- `device_or_channel_switch_flag` (bool) — optional, only if time allows

### 3.5 Razorpay-Aligned Dataset Schema

All synthetic data MUST use Razorpay's exact field naming conventions, ID prefixes, and data formats.

#### ID Format Convention
```python
# Match Razorpay's actual ID formats
import random, string

def razorpay_id(prefix: str, length: int = 14) -> str:
    chars = string.ascii_letters + string.digits
    return f"{prefix}_{''.join(random.choices(chars, k=length))}"

# Prefixes:
# order_  → Orders        (e.g., order_DBJOWzybf0sJbb)
# pay_    → Payments       (e.g., pay_FgR9UMzgmKDvRH)
# rfnd_   → Refunds        (e.g., rfnd_Ax7kQp2mN9rLwE)
# cust_   → Customers      (e.g., cust_1Aa00000000004)
```

#### Amount Convention
```python
# All amounts in PAISE (smallest currency unit), not rupees

# ₹1,499.00 = 149900 paise

```

#### Timestamp Convention
```python

import time
created_at = int(time.time())  # e.g., 1693574400
```

#### 3.6.4 Generation Algorithm (step-by-step)

```
STEP 1: Initialize
  - Set numpy/random seed = 42
  - Create empty lists: customers[], orders[], refunds[]

STEP 2: Generate Customers
  FOR i in range(2500):
    - Assign archetype based on distribution (70/15/10/5)
    - Generate: cust_id (cust_ prefix), email (faker), contact (+91XXXXXXXXXX)
    - Generate: account_created_at (Unix timestamp, based on account_age_days config)
    - Generate: billing_city, shipping_city (for address_mismatch)
    - Append to customers[]

STEP 3: Generate Orders per Customer
  FOR each customer:
    - Draw orders_count from archetype config range
    - FOR each order:
      - Generate: order_id (order_ prefix), payment_id (pay_ prefix)
      - Draw: amount from archetype's amount range
      - Draw: payment_method from archetype's method weights
      - Draw: product_category from archetype's preferred_categories
      - Generate: product_name using Faker (category-appropriate)
      - Draw: promo_code (None or "SAVE20"/"FLAT500"/"WELCOME10") based on promo_usage_rate
      - Generate: created_at (random Unix timestamp within simulation window, AFTER account creation)
      - Set: order_status="paid", currency="INR", payment_captured=true, international=false
      - Append to orders[]

STEP 4: Generate Refunds (subset of orders)
  FOR each order:
    - Draw: should_refund (True/False) based on archetype's refund_probability
    - IF should_refund:
      - Generate: refund_id (rfnd_ prefix)
      - Draw: order_to_return_days from archetype's config range
      - Calculate: refund created_at = order created_at + order_to_return_days (in seconds)
      - Set: refund amount = order amount (full refund — simplification)
      - Draw: return_reason from archetype's return_reasons_weights
      - Draw: return_condition from archetype's return_condition_weights
      - Draw: speed_requested ("normal" 80% / "instant" 20%)
      - Set: status="processed", speed_processed=speed_requested
      - Append to refunds[]

STEP 5: Generate Engineered Features
  FOR each order that has a refund:
    - Calculate return_rate_90d: (refunds in 90-day window) / (orders in 90-day window)
    - Calculate order_to_return_days: (refund.created_at - order.created_at) / 86400
    - Calculate item_value_percentile: percentile rank of this order's amount within customer's order history
    - Set promo_code_used: True if order had promo code
    - Calculate account_age_days: (order.created_at - customer.account_created_at) / 86400
    - Count orders_last_90d: orders in 90-day window before this order
    - Calculate category_return_rate_deviation: z-score of customer's category return rate vs global category return rate
    - Check same_day_reorder_after_return: any order within 24h after this refund?
    - Set address_mismatch_flag: billing_city != shipping_city
    - Set return_reason: from refund's notes_return_reason
    - Set is_abusive_return: 1 if archetype is wardrober or serial_abuser, else 0
    - Set customer_archetype: archetype name (STRIP BEFORE TRAINING)

STEP 6: Apply Label Noise
  - Select 4% of rows randomly
  - Flip is_abusive_return: 0→1 or 1→0
  - This simulates real-world label uncertainty

STEP 7: Also include orders WITHOUT refunds
  - For feature engineering, include non-refunded orders with:
    - is_abusive_return = 0
    - return_rate_90d, orders_last_90d still calculated
```

## 4. Modeling & Evaluation Methodology

### 4.1 Hybrid architecture
- **Rule layer (fast-path, cheap, explainable):** hard rules for extreme cases, e.g. `return_rate_90d > 0.8 AND orders_last_90d < 3` → auto-flag High without needing the model. This gives you an interpretable first line and a fallback if the model is ever unavailable.
- **ML layer (XGBoost classifier):** trained on the full feature set for the harder, non-obvious cases the rule layer doesn't catch.
- **Combination logic:** if rule layer fires → High risk, reason = rule name. Else → use XGBoost probability, banded into Low (<0.3) / Medium (0.3–0.7) / High (>0.7).

### 4.2 Explainability: SHAP (locked in)
- Use `shap.TreeExplainer` for XGBoost — gives per-prediction feature contribution values.
- For each scored order, return SHAP values as part of the response: which features pushed the score up, which pulled it down, and by how much.
- Display as horizontal bar chart in the UI explainability panel.
- Global feature importance (SHAP summary plot) saved as a static asset and displayed in the metrics dashboard.

### 4.3 Train/test protocol
- Stratified 80/20 split on `is_abusive_return`, fixed random seed (document it).
- If time allows: 3-fold stratified cross-validation, report mean ± std of each metric instead of a single number — this alone will put you ahead of most teams.
- **Never** tune hyperparameters on the test set. Use a validation split carved from the training 80% if you need to tune `max_depth`/`n_estimators`.

### 4.4 Metrics to report (all on the held-out set only)
- Precision, Recall, F1 — overall and per-class
- Confusion matrix (raw counts)
- ROC-AUC and PR-AUC (PR-AUC matters more here since the abusive class is a minority class)
- SHAP summary plot (global feature importance — beeswarm or bar)
- Per-prediction SHAP waterfall (shown live in demo for individual scores)

### 4.5 False-positive cost model (mandatory, this is what "the bar" is checking for)
Define a simple, stated cost formula and show the number:

```
cost_of_false_positive = (avg_customer_lifetime_value × churn_probability_if_wrongly_flagged)
                          + (support_ticket_handling_cost if escalated)

cost_of_false_negative = avg_returned_item_value × (1 - resale_recovery_rate)
```

Assign reasonable illustrative values (state them as assumptions, e.g. "assuming ₹150 support cost per wrongly-escalated case and ₹2,000 average customer LTV impact") and compute:
`Total FP cost on test set = false_positive_count × cost_of_false_positive`

This single number, next to your precision/recall table, is the difference between "a model" and "a risk manager."

### 4.6 Threshold selection
Don't default to 0.5. Plot precision-recall vs. threshold and pick the threshold that minimizes `(FP_count × cost_of_FP) + (FN_count × cost_of_FN)` — i.e., pick the threshold that minimizes total business cost, not the one that maximizes accuracy. State this explicitly in the demo — it's a strong, judge-visible signal of "risk manager" thinking rather than "ML homework" thinking.

Pre-compute precision/recall/FP-cost at every 0.01 threshold step and serve as JSON from `/threshold-explore` — this powers the interactive threshold slider in the UI.

## 13. Methodology Notes to Keep Credibility High

- **Never report a single "accuracy" number alone** — always precision/recall/FP-cost together. Accuracy on an imbalanced dataset (which this is, by design) is close to meaningless and a sharp judge will notice if it's the headline number.
- **Show the confusion matrix, not just derived metrics.** Raw counts let a judge sanity-check your claims themselves.
- **Document every assumption in the FP-cost model.** Judges won't fault you for using illustrative numbers — they'll fault you for presenting them as if they were real without saying so.
- **Keep the rule layer's thresholds visible in the pitch.** "Here's the one obvious case we catch with a simple rule, and here's the harder case only the model catches" is a strong two-sentence explainability story.
- **Show SHAP per-prediction in the live demo.** "Here's WHY this specific order was flagged" is the explainability proof judges will remember.
- **The Razorpay API integration is the closer.** End the video with the live transaction demo — most memorable last.
- **Do not add features not in Section 3.4 without sign-off** — feature creep is the fastest way to blow the budget and to accidentally leak label information into features.
